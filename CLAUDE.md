# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

Static HTML mockups for a PWA "gestion de temps" (time-tracking) app, multi-tenant, sold to several small excavation/construction companies. Pilot client: **Excavation J2B**. Editor: BossLabs. There is no application code in this repo (no `src/`, no `web/`) — only design mockups, a Python export script, and reference docs. The real application (a .NET API + Nuxt front end) lives in a **separate repo** not checked out here; don't expect `dotnet`/`npm` commands to work in this working directory.

This branch (`GestionTempsJordanBoucher`) keeps the mockups flat at the repo root (`A-Temps.html`, `source/`, `assets/`, `index.html`) rather than under a `mockups/` subfolder, to match GitHub Pages' "deploy from branch root" setting — don't reintroduce a nested subfolder.

**Read [maquettes-transfert.md](maquettes-transfert.md) first** for full product context — it's a snapshot written 2026-09-22 to let mockup work continue without the app repo on hand. It documents the product, roles, the manifest-driven branding/module system the mockups must respect, and which app files a design change would touch (all in the other repo). Treat its description of `mockups/` contents as unverified against this tree (it says so itself) but its description of the built app as verified against that app's code as of that date — re-verify against the other repo if it matters and time has passed. Note it calls the vendor-mockups folder `mockups-vendeur-prive/`; in this repo that folder is [private-mockups/](private-mockups/) instead.

### Product constraints that should shape any mockup change

- Operators fill this in on a phone, **wearing gloves, in sunlight, often offline** — this beats aesthetics in any tradeoff.
- No color is hardcoded in the real app: `colorPrimary`/`colorSurface`/`colorText` come from each tenant's branding manifest at runtime and must pass a **4.5:1 contrast** check (API-enforced). A mockup that bakes in "gold on black" doesn't generalize — the next tenant might be blue on white.
- The operator home screen shows **at most 4 module tiles**, and the set/labels/order are per-tenant config (e.g. a construction company has no `trip` module; a landscaping tenant renames it "Livraisons"). Mock the home screen so it still works with 2–3 tiles and with longer labels.
- Sync state (pending entries, last sync time) is explicit text, not color-only, and must be visible on every screen — nothing auto-submits, there's always a manual **Synchroniser** action.
- Touch targets ≥ 44px.

## Source of truth vs. published output

Mockups are authored in **Claude's canvas/artifact tool** (`https://claude.ai/artifact/76HFQjZZTuyxzbLzecufRN`), edited there, then exported to this repo as standalone static files.

- `source/*.dc.html` — canvas-format source files (contain `<x-dc>` wrappers, a `<helmet>` block for head content, `<script src="./support.js">`, and `data-dc-script` blocks used by the canvas editor runtime). **Treat these as the authored source**, but note they are exported *from* the canvas, not hand-edited as the primary workflow — substantive design changes normally happen in the canvas itself.
- `source/canvas.json` — layout metadata for the canvas (board titles, positions, sizes, `order` of boards).
- `source/export-standalone.py` — converts every `.dc.html` source into a standalone `*.html` file at the repo root and regenerates the root `index.html`. Run it from inside `source/`:
  ```bash
  cd source
  python export-standalone.py
  ```
  It strips the canvas runtime (`support.js`, `<x-dc>`, `<helmet>`, `data-dc-script`), inlines the head content, replaces `{{accent}}` with the accent color constant, rewrites canvas blob URLs to `assets/...` paths, and rewrites internal `href="X.dc.html"` links to `href="X.html"`.
- `*.html` at repo root — generated, standalone, self-contained mockup pages. **Do not hand-edit these directly**; edit the corresponding `source/*.dc.html` and re-run the export script instead, or changes will be lost on the next export.
- `index.html` at repo root — generated gallery page embedding every mockup in iframes, grouped by design option (A/B/C). Regenerated by the same script — do not hand-edit. This is what GitHub Pages serves.
- `assets/` — logo images referenced by the standalone pages via relative paths (`assets/...`). Never change these to `../assets/...`: the repo root is published standalone via GitHub Pages and has no parent directory on the published site.

## Design options and roles

Three parallel, **undecided** visual directions — no design has been chosen yet, which is why the real app's CSS is deliberately plain/unstyled (any option can be applied without touching app logic):

- **A** — "Cadran": inspired by the client's hand sketch — dark, circular hub-of-buttons home screen, company logo centered.
- **B** — "Chantier": a different, freer direction — light theme, tab bar, dense lists.
- **C** — "Journée": a different, freer direction — dark theme, day-feed style, sheet-based entry forms.

Within each option, screens are duplicated per role: **bluehat** (operator — enters time/trips/materials/photos/notes on job sites already assigned to them), **whitehat** (foreman — everything bluehat does, plus calendar, creating job sites/clients, seeing everything entered on a site), and **admin** (everything whitehat does, plus configuring trip types/vehicles/materials/settings, and CSV export of a job site). A fourth role, **vendeur** (reseller/editor console — outside any tenant, opens new companies, sells them modules, sets their colors, views usage), only has mockups in [private-mockups/](private-mockups/), not in the published set at the repo root.

Job sites (chantiers) carry an **état** (Actif / En pause / Terminé): shown as a read-only badge everywhere a chantier is listed, but only editable from the whitehat/admin "nouveau chantier" screen (bluehat never reaches that screen, so the constraint is enforced by role routing, not a disabled control). CSV export only lists chantiers marked Terminé.

Common screens across options (9 per option, 27 total): accueil bluehat, accueil whitehat, accueil admin, calendrier (whitehat), ajout d'un voyage, saisie de temps, ajout d'un chantier, configuration admin (mobile), configuration admin (PC — wider layout, `*-Config-PC.html`). The **Synchroniser** button and "autre/matériaux" entry were folded into these same screens in a later pass, not added as separate screens. Two screens the mockups show have no equivalent in the real app yet: photo capture (waiting on storage) and correcting an existing entry (API exists, no screen calls it).

File naming follows `<Option>-<Role/Screen>.html`, e.g. `B-Chantier-Detail.html`, `C-Whitehat-Semaine.html`. `Main.html` is option A's bluehat home screen (kept unprefixed for historical reasons — it's still listed under "Option A" in the index).

## `private-mockups/`

The **vendeur** role's mockups: four style variants (A–D) of the multi-tenant company-management console (`/vendeur` in the real app — PC only, refuses below 1024px width). It is **not** part of the published gallery and **not** in the Claude canvas — it has its own `.gitignore` containing `*`, so its contents (including its own `README.md`) are intentionally untracked by git. This was an explicit client request ("don't publish this by accident"); don't assume anything here is version-controlled, and if asked to make it tracked, confirm first since that reverses a deliberate client ask — it means deleting `private-mockups/.gitignore`.

## Conventions when editing mockup markup

- Pages are single self-contained HTML files with inline `<style>` and inline element styles — no CSS files, no JS framework, no build step for the mockups themselves. Plain `<script>` blocks (not tagged `data-dc-script`) survive the export untouched, so real interactivity (see below) belongs there, not in inline `onclick` handlers.
- Google Fonts are loaded per-option via `<link>` in the head (e.g. Oswald+Karla for option A); keep font choice consistent within an option when adding screens.
- The accent color is a literal hex value in exported files (`export-standalone.py` replaces the `{{accent}}` placeholder with `#E9A82C` at export time) — in source `.dc.html` files, use `{{accent}}` rather than hardcoding the hex so the export substitution keeps working.
- Internal navigation links between mockup screens use plain `<a href="X.dc.html">` in source (rewritten to `.html` on export) — don't link with `.html` extensions inside `source/*.dc.html`.
- **Option A's sub-pages open like a bottom sheet**: pages reached via a "+"/action tap from a home/hub screen (`A-Temps`, `A-Voyage`, `A-Materiaux`, `A-Chantier-Add`, `A-Config`) use the `.a-sheet` class + `sheet-in`/`sheet-out` keyframes (slide up from `translateY(100%)` on load) and an X (`.a-sheet-close`) instead of a back arrow, which slides the sheet back down before navigating. Root/nav destinations reached directly from a hub (home screens, `A-Calendrier`, `A-Config-PC`) don't get this treatment. Copy the existing `<style>`/`<script>` blocks verbatim into any new sub-page rather than reinventing them.
- **Type/material pickers use a searchable combobox, not a chip grid, once the option list exceeds 8 items** (see `TYPE DE TEMPS`/`SORTE DE VOYAGE`/`MATÉRIEL` in `A-Temps`/`A-Voyage`/`A-Materiaux` for the reference implementation: `.combo`/`.combo-field`/`.combo-panel`/`.combo-option` classes + inline filter script). Note `.combo-option[hidden] { display: none; }` is required — the plain `.combo-option { display: block; }` rule otherwise overrides the browser's default `[hidden]` styling and the filter silently stops hiding non-matching rows.
